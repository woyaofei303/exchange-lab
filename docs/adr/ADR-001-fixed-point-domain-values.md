# ADR-001: 金额与精度使用固定小数表示

- 状态：已采纳
- 日期：2026-08-10
- 决策范围：价格、数量、金额、名义价值及后续保证金与盈亏

## 背景

永续合约系统需要对价格、数量、资产金额和最小下单额进行可重复、可审计的计算。二进制浮点数无法精确表示很多十进制小数，例如 `0.1`；相同业务值经过不同计算顺序后可能得到不同结果。交易校验、账本和数据库如果对 scale 的理解不一致，还会产生 10 倍、100 倍甚至更大的单位错误。

## 决策

1. Go 领域类型使用 `int64 atoms + uint8 scale` 作为权威值：
   - `真实值 = atoms / 10^scale`；
   - `Asset` 定义资产账本 scale；
   - `Instrument` 定义价格 scale、数量 scale、价格步长、数量步长和最小下单额；
   - `Price`、`Quantity`、`Money` 的字段保持私有，只能通过十进制字符串构造。
2. 领域输入只接受普通十进制字符串，不接受 `float32`、`float64`、科学计数法、隐式舍入或隐式 scale 转换。
3. scale 上限为 18。任何无法放入 `int64 atoms` 的输入都返回 `ErrOverflow`，不截断、不回绕。
4. 价格乘数量时使用 `math/big.Int` 作为中间计算，防止 `int64` 中间乘法溢出；结果必须能够精确转换到报价资产 scale，否则返回 `ErrPrecisionExceeded`。
5. 第 2 周不定义舍入规则。需要舍入的业务必须在后续 ADR 中明确舍入方向、发生位置和会计含义，在此之前一律失败。
6. 后续 PostgreSQL 表必须显式表达单位和 scale：优先使用 `*_atoms BIGINT`，并通过对应的 `*_scale SMALLINT`、资产元数据或合约元数据约束其含义。禁止使用 `REAL` 或 `DOUBLE PRECISION` 保存账务、价格、数量、保证金和盈亏真值。
7. `make domain-check` 使用 Go AST 扫描 `internal/trading`，禁止出现 `float32`、`float64` 类型标识符和浮点字面量。

## 为什么 Go 与数据库都必须明确 scale

Go 的 `1000` 可能代表 `10.00`、`1.000` 或 `1000`；数据库中的 `BIGINT 1000` 也有同样歧义。只有双方共享明确的 scale，序列化、比较、步长校验、重放和审计才具有唯一解释。scale 属于领域契约，而不是展示格式。

## 示例

```text
价格：50000.10，price_scale=2，price_atoms=5000010
数量：0.001，quantity_scale=3，quantity_atoms=1
名义价值：50.00010000 USDT，asset_scale=8，money_atoms=5000010000
```

## 被拒绝的方案

- `float64`：简单但不能保证十进制精确性，比较与累计结果不可审计。
- 只用字符串：可保留输入，但比较、步长和乘法会把解析复杂度扩散到所有调用方。
- 立即引入第三方 decimal 依赖：第 2 周所需能力可由标准库完成；新增依赖会扩大供应链、序列化和升级成本。
- 在数据库使用 `NUMERIC`、在 Go 使用浮点数：数据库精确并不能修复应用层在写入前已经产生的误差。

## 影响

- 优点：精确、可重放、错误显式，调用方无需自行处理单位换算和步长规则。
- 代价：每个值都必须携带或引用 scale；超大值和需要舍入的运算会失败，需要调用方处理领域错误。
- 后续：数据库迁移、保证金、手续费、资金费率和盈亏模型必须遵循本 ADR，或通过新的 ADR 明确替代方案。
